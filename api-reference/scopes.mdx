Scopes control what your credential can access. Each endpoint requires a specific scope. If your credential doesn't carry it, the API returns `403 Forbidden`. It never returns partial data or silently omits fields. Designing around scopes from the start keeps your integration predictable and limits the blast radius if a token leaks.

## Available scopes

| Scope               | Required for                                              | Grants                                       | Plan |
| ------------------- | --------------------------------------------------------- | -------------------------------------------- | ---- |
| `profile.read`      | `GET /profile`, `GET /services`, `GET /services/{slug}`   | Public profile, username and services        | Free |
| `availability.read` | `GET /availability`                                       | Available time slots                         | Free |
| `bookings.read`     | `GET /bookings`, `GET /bookings/{id}`                     | Existing bookings                            | Pro  |
| `invites.read`      | `GET /invites`, `GET /invites/{id}`                       | Single-use links                             | Free |
| `invites.write`     | `POST /invites`, `DELETE /invites/{id}`                   | Create and delete single-use links           | Free |

## Plans

What a credential can do depends on the plan of the Tikk account it belongs to, not on the developer who built the app.

- Free scopes work on every plan.
- Pro scopes can be granted on any plan, but only work while the account is on Tikk Pro. Calls from a Free account return `403` with `"error": "plan_required"`:

```json
{
  "message": "This endpoint requires the Tikk account to be on the Pro plan.",
  "error": "plan_required",
  "required_plan": "pro",
  "upgrade_url": "https://app.tikk.chat/billing"
}
```

Nothing needs to be reconnected or reissued when the plan changes. After an upgrade the same credential works immediately. After a downgrade, Pro calls return `plan_required` again.

To adapt your UI up front, read `plan` from [`GET /profile`](/api-reference/profile/get-profile). Pro scopes only work when it is `pro`.

## API keys

When you create a key under **Settings → API Keys**, you choose which scopes it carries. Pick at least one. A key can only call endpoints for the scopes you gave it. You can have up to 10 active keys.

## OAuth tokens

When building a partner app, request only the scopes your integration actually needs. You choose your app's scopes when you register it in the [developer portal](https://developer.tikk.chat). Specify them in the `scope` query parameter on the authorization URL as a space-separated list:

```text
https://app.tikk.chat/oauth/authorize
  ?client_id=YOUR_CLIENT_ID
  &redirect_uri=https://yourapp.com/callback
  &response_type=code
  &scope=profile.read bookings.read
```

The user sees exactly which scopes your app is requesting on Tikk's consent screen. The resulting access token only carries the scopes you requested, even if the user's account has broader permissions.

## Missing scope response

If you call an endpoint without the required scope, the API responds with `403 Forbidden` and the following body:

```json
{
  "message": "Missing required scope.",
  "scopes": ["bookings.read"]
}
```

`scopes` lists the scope or scopes the endpoint needs. A credential that holds the scope but sits on a Free account gets `plan_required` instead. See [Plans](#plans). Check the [Errors](/api-reference/errors) page for the full list of error codes and their meanings.

<Tip>
  Request the minimum scopes your integration needs. Fewer scopes means smaller
  impact if a token leaks. An attacker with a `profile.read`-only token can't
  reach bookings data or create invites.
</Tip>
